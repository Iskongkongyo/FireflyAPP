📘 文档概览 Documentation Overview

把 FireflyApp 理解成三层会比较容易：项目层、预览层、打包层。项目层负责保存配置，预览层负责实际运行网站，打包层负责生成最终 APK。

Think of FireflyApp in three layers: project, preview/runtime, and pack. The project layer stores configuration, preview runs the site, and pack generates the final APK.

🧭 完整流程 End-to-End Workflow

FireflyApp 的推荐使用流程其实很稳定：先建项目，再做基础配置，再预览，最后打包。下面这套流程适合大多数场景。

The recommended FireflyApp workflow is stable: create a project, configure the basics, preview, then pack. This sequence fits most use cases.

1

创建项目

Create a project

从 项目中心 新建项目，先填一个易读的项目名。项目名主要影响管理体验，最终安装后显示的应用名称可以在 编辑 页单独设置。

Create a new project from Project Hub. Use a readable internal name. The installed app name can be changed later in Build.

2

先完成基础页

Finish the Basic tab first

先把默认 URL、模板、导航、浏览器行为、安全策略配好。很多预览问题都不是“代码错了”，而是 基础页参数之间有冲突。

Set the default URL, template, navigation, browser behavior, and security first. Many preview issues come from conflicting Basic settings.

3

再补规则 / 事件 / 品牌 / 构建

Then move to Rules / Events / Branding / Build

页面规则、页面事件、品牌资源和打包身份建议放在第二轮做，因为它们依赖你先确定整体模板和导航结构。

Rules, events, branding, and build identity are best handled after the overall template and navigation structure are settled.

4

预览验证

Preview and validate

预览时重点观察：导航切换、权限提示、加载浮层、错误页、夜间模式、状态栏颜色、网站对 WebView 的兼容性。

During preview, focus on navigation transitions, permission prompts, loading overlay, error pages, dark mode, system bar colors, and site compatibility.

5

准备 → 打包 → 安装

Prepare → Pack → Install

准备 会先准备模板工作区并刷新预检查；打包 才是真正生成 APK；安装 / 分享 则基于最新成功输出的产物。

Prepare builds the workspace and refreshes preflight. Pack generates the APK. Install and Share operate on the latest successful output.

🏠 项目中心 Project Hub

项目中心 是宿主 App 的入口页，也是你管理多个项目的地方。它负责项目列表、导入导出、语言切换、帮助入口和 打包 跳转。

Project Hub is the host app home screen. It manages your projects, import/export actions, language selection, help access, and Pack entry points.

顶部概览

Top dashboard

展示项目数量、最近项目和一些快捷入口。更像工作台，不直接影响打包结果。

Shows project count, latest project, and quick actions. It is mainly a workspace summary.

项目卡片

Project cards

每个卡片通常会提供进入编辑器、预览、导出和 打包 等动作。以后你修改同一个项目，大多数时候都从这里进入。

Each card provides actions such as open editor, preview, export, and Pack. Most repeated work starts here.

侧边工具

Side tools

帮助文档、图标设计器、图标仓库、语言切换和 About 都在这里。对项目内容无害，适合随时进入查看。

Help docs, icon designer, icon catalog, language switch, and About live here. They are safe utility entries.

🛠️ 配置编辑器 Config Editor

配置编辑器是整个项目的控制台。大多数用户会在这里完成 80% 以上的工作。它按标签页拆分功能，目的是让复杂配置更容易组织。

Config Editor is the project control center. Most work happens here. It splits features into tabs so complex configuration stays organized.

六个标签页分别做什么

What each tab is for

  • 基础：项目骨架，先确定模板、导航、浏览器、安全策略
  • 规则：给特定 URL 套特殊行为
  • 事件：监听页面生命周期，触发动作
  • 品牌：应用图标、启动图、栏位颜色、抽屉图片等视觉资源
  • 构建：应用身份、输出命名、签名
  • JSON：高级编辑模式，也是最终配置真相源
  • Basic: the project skeleton: template, navigation, browser, security
  • Rules: special behavior for specific URLs
  • Events: lifecycle listeners and actions
  • Branding: icons, splash, bar styling, drawer images, visual assets
  • Build: app identity, output naming, signing
  • JSON: advanced editing mode and the final source of truth

编辑器里需要记住的几个通用动作

Universal editor actions

保存 Save 重置 Reset 导入 Import 导出 Export 预览 Preview

保存会把当前可视化状态写回项目配置；重置会恢复到默认示例；导入导出适合做版本备份；Preview 适合做行为验证。

Save writes current visual state back to project config. Reset restores bundled defaults. Import/export are useful for backups. Preview validates real behavior.

代码编辑器增强

Code editor enhancements

  • 全局 JS / CSS、规则 JS / CSS、按钮 运行 JavaScript、事件 运行 JavaScript 都支持进入全屏代码编辑器
  • 全局 JS / CSS 与规则 JS / CSS 已支持多代码块编辑，可新增、复制、排序、删除
  • JS 编辑器右上角 + 可插入常用片段，如 fetch、等待元素出现、事件变量模板等
  • Global JS/CSS, rule JS/CSS, button run_js, and event run_js can all open in a fullscreen code editor
  • Global and rule JS/CSS now support true multi-block editing with add, duplicate, reorder, and delete
  • The JS editor has a + menu for common snippets such as fetch, wait-for-element helpers, and event-variable templates
如果你发现可视化表单里没有你想调的字段，先不要怀疑功能不存在。很多高级字段仍然可以在 JSON 标签页里直接编辑。 If a field is missing from the visual form, do not assume the feature does not exist. Many advanced fields are still available directly in the JSON tab.

⚙️ 基础页：先把骨架搭好 Basic Tab: Build the skeleton first

基础页是最重要的页面。推荐顺序是：先定模板，再定导航，再定浏览器行为，最后定安全策略。很多问题都可以在这里提前规避。

The Basic tab is the most important screen. Recommended order: choose the template, define navigation, set browser behavior, then security. Many issues can be prevented here.

1. 应用 区域

1. App section

  • 项目名称 是项目内部名字，不等于最终安装后的应用名称
  • 模板 决定外层壳结构，后续很多参数会跟着变化
  • 默认URL 是单页模板的主入口，也是很多规则和事件的起点
  • Project name is the internal project label, not necessarily the final installed app name
  • Template decides the outer shell, and many later options depend on it
  • defaultUrl is the main entry for single-page shells and often the base for rules and events

2. 导航 区域

2. Navigation section

  • 导航项最多支持 5 个
  • 每项至少要考虑：id、标题、URL、图标、选中图标
  • 如果某个模板不支持原生导航，导航项不会渲染出来
  • defaultNavigationItemId 可指定默认打开哪个导航
  • Up to 5 navigation items are supported
  • Each item should at least define: id, title, URL, icon, and selected icon
  • If the chosen template does not support native navigation, items will not render as bars or tabs
  • defaultNavigationItemId chooses the first navigation item to open

3. 导航相关的高级设置

3. Advanced navigation settings

  • 启用滑动切换导航：允许左右滑动切换相邻导航项
  • 导航预加载数量：后台预加载相邻导航根页，减少首次切换等待
  • 保留当前导航页栈：保留当前导航项内最近页面栈
  • 导航返回行为：决定返回键优先走网页历史还是先回首页导航
  • Enable swipe navigation: allows left/right switching between adjacent navigation items
  • Navigation preload count: preloads nearby root pages in the background
  • Preserve current navigation page stack: keeps recent pages inside the current navigation item
  • Navigation back behavior: decides whether back prefers web history or returns to the home navigation item first

4. 这些导航开关之间会互相影响

4. These navigation toggles affect each other

  • 启用导航预加载后，返回行为会固定为“切换导航时重置”
  • 启用“保留当前导航页栈”后，也会倾向于锁定导航返回行为
  • 预加载页面在真正打开前不会记入网页历史，隐藏页下载、权限、外跳等副作用会被抑制
  • When navigation preload is enabled, back behavior is fixed to reset-on-navigation
  • Preserving the current navigation stack also constrains navigation back behavior
  • Preloaded pages stay out of web history until first real visit, and hidden-page side effects are suppressed

5. 浏览器 区域

5. Browser section

  • 允许页面缩放：开启后支持双指缩放
  • 显示加载浮层：切到慢页面时显示加载浮层
  • 显示加载进度条：显示顶部加载进度条
  • 显示错误页：加载失败时显示宿主错误页
  • 夜间模式：关闭 / 开启 / 跟随主题
  • 屏幕方向：不限制 / 强制竖屏 / 强制横屏
  • 沉浸式状态栏：是否让内容更贴近状态栏
  • userAgent：只在确实需要伪装设备类型时再改
  • allowPageZoom: supports two-finger zooming when enabled.
  • showLoadingOverlay: shows a loading overlay when switching to slow pages
  • showPageProgressBar: shows the top loading progress bar
  • showErrorView: displays the host error page when loads fail
  • nightMode: off / on / follow_theme
  • screenOrientation: unspecified / portrait / landscape to keep rotation free, force portrait, or force landscape
  • immersiveStatusBar: controls whether content reaches into the status bar area
  • userAgent: only change this when you truly need to emulate another device/browser profile

6. 安全 区域

6. Security section

  • 允许的Hosts 是第一道限制，决定哪些域名允许在壳内加载
  • 允许外部Hosts 为关时，白名单外 URL 会被严格处理
  • 启用原生KV桥 用来控制是否向页面暴露 NativeBridge
  • KV可信Hosts 是独立于 允许的Hosts 的第二道限制，只决定哪些 host 能访问原生 KV
  • 打开其他应用 支持 询问 / 允许 / 拦截
  • SSL证书错误处理 支持 严格校验 / 忽略SSL证书错误，默认建议严格校验
  • allowedHosts is the first barrier that decides which domains may load inside the shell
  • When allowExternalHosts is off, URLs outside the whitelist are handled strictly
  • Enable Native KV bridge controls whether the page receives the NativeBridge interface
  • kvTrustedHosts is a second, separate gate from allowedHosts, and only decides which hosts may access native KV
  • openOtherAppsMode supports ask / allow / block
  • sslErrorHandling supports strict / ignore, and strict is recommended

7. 顶栏按钮行为

7. Top-bar button behaviors

  • 带顶栏模板支持控制返回、首页、刷新按钮是否显示
  • 返回按钮支持 默认返回动作、默认首页、默认导航项、执行 JavaScript
  • 首页和刷新按钮也支持原生行为与 运行 JavaScript 结合
  • 当按钮行为设为 运行 JavaScript 时，会打开全屏代码编辑器，适合写较长脚本
  • Templates with a top bar can control whether back, home, and refresh buttons are shown
  • The back button supports default_back, default_home, default_navigation_item, and run_js
  • Home and refresh buttons also support both native behaviors and run_js
  • When a button is set to run_js, it opens in the fullscreen code editor for longer scripts
最常见的基础页误区：网站能在浏览器里打开，不代表它就应该被放进 允许的Hosts 之外的跳转流程里。很多外链、登录跳转、支付流程都要结合安全策略一起测。 A common Basic-tab mistake: just because a site opens in a browser does not mean it should be left outside the intended allowedHosts flow. External links, login redirects, and payments should be tested together with security settings.

🧾 app-config.json 详细配置说明 Detailed app-config.json Reference

app-config.json 是项目真正的配置真相源。可视化编辑器只是它的友好外壳。理解这份 JSON 后，你会更容易处理批量修改、高级字段和导入导出问题。

app-config.json is the real source of truth for a project. The visual editor is only a friendly shell around it. Once you understand the JSON, advanced edits and import/export workflows become much easier.

app 与 browser

app and browser

  • app.name：默认应用名
  • app.template：模板类型，如 top_bar_bottom_tabs
  • app.defaultUrl：默认入口 URL
  • browser.showLoadingOverlay：是否显示加载浮层
  • browser.showErrorView：是否显示错误页
  • browser.nightMode：no / yes / follow theme
  • browser.screenOrientation：unspecified / portrait / landscape
  • browser.immersiveStatusBar：是否启用沉浸式状态栏
  • app.name: default app name
  • app.template: template type, such as top_bar_bottom_tabs
  • app.defaultUrl: default entry URL
  • browser.showLoadingOverlay: whether to show the loading overlay
  • browser.showErrorView: whether to show the host error page
  • browser.nightMode: off / on / follow_theme
  • browser.screenOrientation: unspecified / portrait / landscape
  • browser.immersiveStatusBar: whether to use immersive status bar layout

navigation 与 shell

navigation and shell

  • navigation.items：导航项数组
  • navigation.items[].id：导航唯一 ID，给默认导航和事件匹配用
  • navigation.items[].selectedIcon：选中状态图标，可留空回退
  • shell.enableSwipeNavigation：启用导航滑动切换
  • shell.navigationPreloadCount：后台预加载相邻导航页
  • shell.topBarThemeColor / bottomBarThemeColor：栏位主题色
  • shell.topBarBackBehavior / topBarHomeBehavior / topBarRefreshBehavior：顶栏按钮行为
  • navigation.items: array of navigation items
  • navigation.items[].id: unique navigation ID used by defaults and matching logic
  • navigation.items[].selectedIcon: selected-state icon, optional
  • shell.enableSwipeNavigation: enables swipe navigation switching
  • shell.navigationPreloadCount: preloads nearby navigation pages in the background
  • shell.topBarThemeColor / bottomBarThemeColor: bar theme colors
  • shell.topBarBackBehavior / topBarHomeBehavior / topBarRefreshBehavior: top-bar button behaviors

security 与 inject

security and inject

  • security.allowedHosts：允许在壳内加载的域名白名单
  • security.allowExternalHosts：是否放行白名单外 URL
  • security.enableNativeKvBridge：是否启用 NativeBridge 原生 KV
  • security.kvTrustedHosts：允许访问原生 KV 的 host 列表
  • security.openOtherAppsMode：ask / allow / block
  • security.sslErrorHandling：strict / ignore
  • inject.globalJs：所有页面共享的 JS 注入
  • inject.globalCss：所有页面共享的 CSS 注入
  • 可视化编辑器已支持多代码块编辑和全屏代码编辑；JSON 页仍然是最适合做最终核对和批量修改的地方
  • security.allowedHosts: host whitelist allowed inside the shell
  • security.allowExternalHosts: whether non-whitelisted URLs may proceed
  • security.enableNativeKvBridge: whether the NativeBridge native KV bridge is enabled
  • security.kvTrustedHosts: list of hosts allowed to access native KV
  • security.openOtherAppsMode: ask / allow / block
  • security.sslErrorHandling: strict / ignore
  • inject.globalJs: JS injected into all pages
  • inject.globalCss: CSS injected into all pages
  • The visual editor now supports multi-block and fullscreen code editing; the JSON tab is still the best place for final verification and bulk edits

pageRules 与 pageEvents

pageRules and pageEvents

  • pageRules[].match：按 URL 等于 / 前缀 / 包含 来匹配页面
  • pageRules[].overrides：覆写标题、栏位显示、错误页、注入等
  • pageEvents[].trigger：事件触发器，如 page_finished
  • pageEvents[].actions：动作列表，如 toast、run_js、load_url
  • 这两部分最适合处理“某些页面要特殊对待”的需求
  • pageRules[].match: matches pages by URL equals / prefix / contains
  • pageRules[].overrides: overrides title, bar visibility, error page, and injections
  • pageEvents[].trigger: event trigger such as page_finished
  • pageEvents[].actions: action list such as toast, run_js, or load_url
  • These two sections are best for “special handling on specific pages”

📦 打包 页：从项目到 APK Pack Page: From project to APK

Pack 页不是一个按钮，而是一整套流程。建议把它理解成“工作区准备 → 预检查 → 重打包 → 签名 → 安装/分享”。

The Pack page is not a single action. It is a pipeline: workspace preparation, preflight, repack, signing, and finally install/share.

1

准备

Prepare

解包模板 APK，注入当前项目配置与资源，准备工作区。你可以把它理解成“为这次打包搭一个临时工位”。

Unpacks the template APK, injects current project assets/config, and prepares the workspace for this build.

2

预检查

Preflight

检查最终包名、签名、已安装版本、版本号、是否存在覆盖更新冲突。这一步能提前发现“安装不了”的原因。

Checks output package identity, signing, installed versions, version code, and update conflicts before actual packaging.

3

打包

Pack

执行模板 APK 重打包、二进制 Manifest 修补、zipalign 和签名。最终会生成一个最新成功产物。

Runs the template APK repack, binary manifest patching, zipalign, and signing, then generates the newest successful artifact.

4

安装 / 分享

Install / Share

安装和分享都依赖最新成功输出的 APK。安装前如果系统提示未知应用安装权限，需要先在系统设置里授权宿主。

Install and Share both use the latest successful APK. If Android asks for unknown-app installation permission, grant it to the host app first.

打包页里常见的信息区块

Common Pack-page panels

  • 项目摘要：项目名、包名、模板、版本信息
  • 预检查：可直接安装、可覆盖更新、签名冲突、版本降级等状态
  • 执行/日志：当前任务状态和打包日志
  • 产物 / 历史：最终 APK 路径和历史产物记录
  • Project Summary: project name, package, template, version info
  • Preflight: install-ready, update-compatible, signature conflicts, version downgrade, etc.
  • Execution / Log: current job status and pack log
  • Outputs / History: final APK path and previous successful artifacts

为什么要看 打包日志

Why Pack Log matters

  • 能看出失败发生在工作区准备、打包、签名还是自检阶段
  • 如果 包管理器 拒绝 APK，日志通常会先给出提示
  • 安装冲突、版本回退、签名不一致等问题，日志比表面 Toast 更完整
  • It shows whether failure happened during workspace prep, packaging, signing, or artifact checks
  • If PackageManager rejects the APK, the log usually explains it first
  • Install conflicts, downgrade issues, and signer mismatches are easier to understand from the log than from a toast alone

敏感权限设置

Sensitive Permission Settings

  • Pack 页里的 敏感权限 开关只影响最终打包生成的 APK，不影响宿主里的项目预览。
  • 默认保留 INTERNET(网络) 和 POST_NOTIFICATIONS(通知)；相机、麦克风、定位可以按项目需要手动开启或关闭。
  • 关闭某项后，最终 APK 的 Manifest 不再声明对应权限，相关网页能力会被直接拒绝，不会继续请求系统授权。
  • 老项目会先沿用历史权限默认值；当你第一次修改并保存这些开关后，项目才会迁移到新的敏感权限规则。
  • The Sensitive Permissions switches on the Pack page affect only the final packaged APK, not project preview inside the host app.
  • By default, INTERNET and POST_NOTIFICATIONS stay enabled. Camera, microphone, and location can be toggled per project.
  • If a permission is turned off, the final APK manifest no longer declares it, and related web capabilities are denied before any Android permission request is shown.
  • Older projects keep their legacy permission defaults first. They move to the new sensitive-permission rules only after you change and save these switches.

团队协作建议：如果你要把项目发给别人继续改，优先导出整个项目包，而不是只导出 app-config.json。这样图标、启动图、抽屉壁纸和签名信息才更完整。 Teamwork tip: if someone else will continue the project, export the full project package rather than only app-config.json. That way icons, splash assets, drawer images, and signing data are preserved more completely.

🩺 常见问题与排错思路 Troubleshooting and FAQ

这部分更偏“先看哪里、先怀疑什么”。如果你遇到异常，建议先从最贴近现象的条目开始查。

This section is about where to look first and what to suspect first. Start with the item that best matches the visible symptom.

1. 预览里能打开，打包后安装失败怎么办？ 1. Preview works, but the packed APK fails to install ▶
先看 打包 页的 预检查 和 打包日志。优先排查：包名冲突、签名不一致、版本号比已安装版本低、系统未授予安装未知应用权限。 Check the Preflight panel and Pack Log first. The usual causes are package conflicts, signer mismatch, version downgrade, or missing “install unknown apps” permission.
2. 切换导航时白屏或切换不跟手怎么办？ 2. Navigation switching feels blank or not responsive enough ▶
先检查是否启用了 启用滑动切换导航 和 导航预加载数量。重页面建议适度开启预加载；轻页面或问题站点可以先把预加载设为 0，再看行为是否稳定。 Check whether Enable swipe navigation and Navigation preload count are enabled. Heavy pages often benefit from preload. For lighter or problematic sites, try setting preload to 0 first and compare behavior.
3. 网站请求定位 / 相机 / 麦克风时表现异常怎么办？ 3. The site behaves strangely when requesting location / camera / microphone ▶
先在 预览 里完整走一遍权限流程，确认是否出现宿主前置提示、系统授权弹窗，以及站点本身的权限确认 UI。再检查相关域名是否确实在可访问范围内。 Run through the full permission flow in Preview first. Confirm the host prompt, system permission dialog, and the site’s own post-grant UI all appear correctly. Then verify the requesting host is actually allowed.
4. 夜间模式下颜色看起来不统一怎么办？ 4. Colors do not look consistent in dark mode ▶
优先检查 夜间模式 是否为 开启 或 跟随主题，再确认顶栏、底栏、标签栏是否使用了自定义浅色主题色。夜间模式下建议尽量避免继续沿用纯白色默认栏位颜色。 First confirm nightMode is set to on or follow_theme. Then inspect whether top, bottom, or tab bars still use custom light colors. In dark mode, avoid forcing pure white bar colors unless you truly want that look.
5. SSL 证书错误怎么处理？ 5. How should SSL certificate errors be handled? ▶
默认建议保留 严格校验。只有在你明确知道目标站点使用的是可信的自签证书或内网证书时，才考虑切换为 忽略SSL证书错误。否则相当于降低了安全门槛。 Keep strict unless you explicitly trust the site’s self-signed or internal certificate. Switching to ignore lowers the safety bar and should be used sparingly.
6. 为什么导入 app-config.json 后，有些资源没跟着来？ 6. Why are some assets missing after importing app-config.json? ▶
因为单独导入 app-config.json 只会带配置，不会带项目图片、图标、启动图、抽屉壁纸、头像等资源。需要完整迁移时，请导入或导出整个 .fireflyproj.zip。 Because importing only app-config.json brings over configuration, not project assets such as icons, splash images, drawer wallpapers, or avatars. Use the full .fireflyproj.zip format for complete transfers.
7. 打包成功了，但更新安装时提示签名冲突怎么办？ 7. Pack succeeds, but update install reports a signer conflict ▶
说明当前输出 APK 的签名证书和已安装版本不一致。解决方式通常有两个：继续使用与旧版本相同的 keystore 重新打包，或者先卸载旧版本再安装新包。 This means the new APK is signed with a different certificate than the installed version. The usual fixes are: rebuild with the same keystore as the old version, or uninstall the old app before installing the new one.
8. 为什么页面里拿不到 NativeBridge，或者调用总是失败？ 8. Why is NativeBridge missing or always failing in the page? ▶
先检查 Enable Native KV bridge 是否开启；再确认当前页面是不是 http/https，且 host 命中了 kvTrustedHosts。如果 trusted hosts 留空，或者页面只是本地页 / 非可信域名页，NativeBridge 就不会按你预期工作。 First check whether Enable Native KV bridge is turned on. Then verify the current page is http/https and its host matches kvTrustedHosts. If the trusted-host list is empty, or the page is local / untrusted, NativeBridge will not behave as expected.
一个很实用的排错顺序：先看 Basic 页是否有冲突设置，再看 Preview 是否能复现，再看 Pack 的 Preflight 和 Log。这样通常能把问题快速缩小到“配置层 / 运行时层 / 打包层”中的某一层。 A practical debugging order: check Basic for conflicting settings, reproduce in Preview, then inspect Pack preflight and logs. This usually narrows the problem down to configuration, runtime, or packaging.
